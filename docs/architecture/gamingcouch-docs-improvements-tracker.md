## Needs planning / discussion

- [ ] **P1 — Visualize the lifecycle events.** *(Needs planning)*
  - Add a diagram of the runtime lifecycle (Setup → `SetupDone` → Play → Playing/inputs+pause → Game
    over) to "How your game runs", so a consumer grasps the flow at a glance.
  - **Open question — rendering target.** The root README is rendered both on GitHub *and* as the docs
    site `/manual/` page (generated by the external DocFX action). GitHub renders Mermaid; DocFX may not
    without a plugin. Decide before authoring: Mermaid, a committed static image (`docs/` asset), or an
    ASCII diagram that renders everywhere. Verify DocFX Mermaid support on the live site first.

- [ ] **P2 — Visualize the HUD / "game view".** *(Needs planning)*
  - Show, at a glance, what the hosted platform renders that the game does not draw itself: player
    nametags, scoreboard, off-screen indicators, and per-player points/meter — and how the game's inputs
    map to it. Goal: a consumer understands the hosted-HUD split without reading the whole HUD section.
  - Include how the anchor components map into it: **`GCPlayerPosition`** tracks a player's normalized
    screen-space coordinates (drives the off-screen indicator and HUD dimming), and **`GCPlayerOverhead`**
    anchors the overhead nametag/points/meter. Illustrate normalized coords (x/y 0→1) and the off-screen
    case.
  - **Open questions:** needs a visual asset (annotated screenshot of a real hosted game, or a diagram).
    Same rendering-target decision as P1. Screenshot sourcing/permission for a public repo.

- [ ] **P3 — Separate internal docs from the consumer-facing repo.** *(Needs planning — discuss)*
  - Problem: the README's **"Internal (platform & DevApp maintainers)"** and **"Decisions & trackers"**
    subsections do not belong in a consumer game-developer's view. Right now they live in the same public
    repo/README because that is the only distribution channel.
  - Proposed direction to discuss: make **this repo private** and publish a **public mirror repo** that
    receives only release-tagged packages and strips internal files (contract docs, ADRs, trackers,
    architecture/planning). Requires restructuring the repo so internal vs public content is cleanly
    separated, while keeping the public mirror installable as a Unity package (UPM git URL) — same
    `package.json`/layout constraints, splash/logo removal, docs-site generation.
  - **Open questions:** mirror mechanism (CI on tag → filtered push); what exactly is "public" vs
    "internal" (README + generated API reference + template/runtime vs `docs/contracts`, `docs/adr`,
    `docs/architecture`, `CONTEXT.md`, `AGENTS*`); does the docs-site pipeline move to the mirror; how do
    cross-repo contract links (client/SDK, DevApp) resolve once internal docs are private.
  - **Interim option (no restructure):** trim or collapse the README's internal/decisions subsections
    (e.g. move them to a single `CONTRIBUTING`/`docs/README` entry point not surfaced in the consumer
    guide). Decide whether to do the interim trim now or wait for the full mirror plan.
